# π0.5 TensorRT INT4 量化部署方案

日期：2026-10-07。版本：`w4_plan_20261007_r4`。目标为用户指定的 RTX 4070，推理总显存上限8GB。用户已明确“仅更新方案，暂不实施”。本轮只变更方案文件和目录入口，不安装依赖、不导出模型、不执行校准、不构建引擎、不运行模型或机器人。

唯一部署主线确定为：**同源浮点 π0.5 → ModelOpt AWQ 校准 → 显式 INT4 ONNX → TensorRT 引擎 → Panda 验证 → 微调后重新校准 ECO65＋ZhiXing 模型**。GPTQ 保留同条件质量对照，其结果也须转换成同一 TensorRT 可接受的格式。PyTorch 用于制作和浮点参考；生产推理采用 TensorRT，TensorRT-LLM 不作为默认入口。

## 框架和量化算法的分工

ModelOpt 负责代表数据统计、通道缩放及量化参数搜索；TensorRT 负责解析显式量化图、选择内核、构建和运行 engine。插入 fake quantizer、生成 ONNX 或得到 engine 文件，均不能单独证明真实 INT4 存储、执行覆盖和8GB部署完成。[ModelOpt 量化说明](https://nvidia.github.io/Model-Optimizer/guides/1_quantization.html)

采用 TensorRT 的 INT4 weight-only 路径：权重使用有符号INT4和对称量化，zero point 为0，范围[-8,7]；激活保留高精度。初始block size=128，开发备选64；具体axis、scale形状和转置规则按实际权重布局登记。[TensorRT 量化格式](https://docs.nvidia.com/deeplearning/tensorrt/latest/inference-library/quantized-types-schemes.html)

显式图使用合法 Q/DQ 或预打包 INT4 权重加 DQ。标准 INT4 和 block quantization 要检查 ONNX opset21及以上的对应支持；不能将旧opset13的INT8范例直接当作INT4导出模板。采用强类型图，以显式dtype、cast和Q/DQ表达精度，不依靠全局 `--int8` 或 `--fp16` 开关实现本方案。[TensorRT 显式量化](https://docs.nvidia.com/deeplearning/tensorrt/latest/inference-library/quantized-types-explicit-quantization.html)

标准 TensorRT 的 WoQ 专用于 INT4 GEMM。因此 r3 的视觉“W8权重、浮点激活”不能直接搬成相同含义的原生TensorRT路径。视觉第一版保留浮点；后续可比较视觉 Linear INT4 WoQ，或另行校准的视觉 INT8 W8A8。W8A8会增加激活量化误差，必须单列精度验证，不能沿用旧W8A16结论。敏感投影和动作专家仍保留浮点。

## 模块精度和8GB预算

| 模块 | 第一候选 | 进一步压缩候选 |
|---|---|---|
| PaliGemma语言Transformer的目标Linear | AWQ INT4 WoQ，GPTQ同条件对照 | 敏感层回退浮点；重新统计覆盖及预算 |
| SigLIP视觉Transformer | 原BF16／FP32精度 | Linear INT4 WoQ；或独立校准的INT8 W8A8 |
| 动作专家Transformer | 原BF16／FP32精度 | 本方案首轮不量化 |
| embedding、patch/position embedding、跨模态投影 | 原浮点 | 首轮保留 |
| 归一化、softmax、动作I/O、时间MLP和Euler更新 | 保留原精度及FP32稳定计算 | 禁止为压缩自动改低位宽 |
| KV cache | 原浮点，仅当前请求 | 不采用KV量化或长历史缓存 |

FLOAT不代表整模型统一FP16。优先保持同源BF16值、BF16计算及已有FP32稳定层；若某版本或内核要求FP16，先建对应浮点基线并记录误差，再量化，不悄然改变参照。

语言INT4、视觉及专家浮点的理想文件估算约3.974GB，新增scale、打包、对齐及引擎开销另计，暂按4.0–4.3GB权重预算。语言与视觉Linear均INT4的理想估算约3.357GB，属于后续候选，不是已导出的TensorRT大小。engine序列化大小、GPU常驻权重和运行峰值分别测量。

预算统一采用十进制GB；硬上限取8,000,000,000字节和实际设备容量的较小值。TensorRT首轮保留视觉浮点后，内部预算重分配如下，总门槛与r3一致：

| 项目 | 工程预算 |
|---|---:|
| 三个engine的常驻权重、量化元数据及必要持久数据 | 4.3GB |
| 激活、前缀KV cache及context缓冲 | 0.8GB |
| 执行临时工作区、插件和CUDA Graph附加占用 | 0.6GB |
| 推理进程CUDA context和库 | 0.4GB |
| 输入输出、传输和转换暂存 | 0.3GB |
| 推理进程峰值 | 6.4GB |
| 系统、显示及其他GPU进程基线 | 0.8GB |
| 未分配余量 | 0.8GB |
| 总预算 | 8.0GB；设备总峰值目标≤7.2GB |

这些是预算，尚未测量。其他现场占用超过0.8GB时，相应收紧推理额度；不终止其他任务。预算包含冷启动、反序列化、预热、异常恢复和连续运行，不只统计稳定请求。TensorRT builder workspace限制只限制构建时的相关工作区，不是进程总显存上限。

## 按现有π0.5采样流程导出

当前源码已经将图像语言前缀和 `denoise_step` 分开，前缀KV在一次采样中复用。首轮按这一路径划分三个逻辑子图，最终边界必须通过浮点输出核对：

| 子图／engine | 输入和输出 | 执行方式 |
|---|---|---|
| vision | 既定图像张量 → SigLIP图像embedding | 各既定图像槽复用一份视觉权重；投影只在一个子图内持有 |
| prefix | 图像embedding、语言token、mask和位置 → 各层前缀K/V及有效mask | 每次观测执行一次，不走文本自回归generate |
| action_step | 前缀K/V、mask、噪声动作、时间embedding → 速度场及／或下一步动作 | 同一engine复用10次，保留原FP32 Euler更新 |

宿主负责tokenizer、图像处理、归一化、固定步数调度和OpenPI协议。常规请求只返回最终动作，不把每步K/V或中间动作复制回CPU。若将Euler更新合入action_step，必须登记融合前后的浮点差异；不将10次循环展开为重复持有权重的十份子模型。

状态接口仍为8维；本π0.5配置的 `discrete_state_input=False`。内部动作 `[1,10,32]`，环境输出 `[10,7]`，horizon=10、去噪10次、20Hz、每5步重规划。图像仍保留双相机输入和原约定的第三占位槽及mask，不能因其图像为零就自动删除分支。token长度、padding、RoPE和注意力mask保持原规则。

HF cache对象在导出适配器中转为明确命名的张量，不把Python对象作为engine接口。每层K/V的形状、dtype、布局和生命周期在N0登记。action_step对前缀cache只读，不在每轮追加动作token或累积历史；执行前后核对长度和内容。

当前时间正弦嵌入存在FP64中间计算。首轮从同源浮点的实际FP32时间序列预计算10个最终时间embedding，并作为浮点输入传入action_step；这只移出重复计算，不能改成未经核对的精确十进制时间表。AdaRMSNorm、门控、残差及FP32归一化均显式保留。导出不支持的算子先做等价图分解并检查浮点误差，插件仅在确有必要时另行登记。

batch=1；优先固定合法token长度及图像分辨率，按既有padding处理。确需动态shape时只登记合法范围内的窄profile，并验证所有边界。mask值不能因shape固定被常量化，也不能截断合法prompt以满足预算。

## 校准和图格式检查

AWQ首选 ModelOpt 的ONNX INT4路线或经验证的PyTorch校准＋ONNX导出。当前ONNX接口只支持目标MatMul，提供 `awq_lite` 通道缩放搜索和 `awq_clip` 裁剪；显式提供真实CalibrationDataReader，并设 `use_zero_point=False`。不提供reader时可能使用随机输入，因此该缺省行为禁止进入任务校准。[ModelOpt ONNX INT4接口](https://nvidia.github.io/Model-Optimizer/reference/generated/modelopt.onnx.quantization.int4.html)

先以128–256个完整Panda开发观测探测覆盖，再扩大到约2,000–5,000个独立开发观测。使用实际图像、任务指令、冻结预处理、相同噪声和完整10步去噪流程。校准prefix子图时提供从同源视觉流程得到的embedding；视觉量化候选必须用真实机器人图像。按任务及接近、抓取、搬运、放置、释放阶段分层，不使用WikiText或随机图像代替。

白名单由原Linear清单映射到实际ONNX节点，记录矩阵形状、axis、block、scale及跳过原因。若Linear导出为Gemm而工具只量化MatMul，先验证等价分解；模型超过2GB使用external data并一起绑定指纹。量化搜索不能被后续普通RTN重写后仍宣称AWQ。

AWQ缩放变换逐一检查所有消费者，无法合法折叠时保留显式缩放或浮点层。GPTQ从同源浮点重新制作对称、block兼容的INT4结果，再导出同一Q/DQ表达；不把GPTQ专用packed模块直接交给ONNX parser。排序或置换须明确还原或入图验证。若适配失败如实保留未通过，不以RTN结果替代GPTQ。

TensorRT/ModelOpt已有视觉量化范例不代表本项目SigLIP或完整π0.5直接受支持；通用范例可能自动改变Conv2d精度。首轮patch embedding保留浮点，后续视觉量化仍使用本项目层白名单，避免继承范例的自动激活量化。[NVIDIA PyTorch到ONNX范例](https://github.com/NVIDIA/Model-Optimizer/blob/main/examples/torch_onnx/README.md)

校准、敏感层筛选、开发验证和正式测试按轨迹／场景隔离。微调后先合并LoRA并确认浮点达标，再用ECO65＋ZhiXing训练划分重新校准；不复用原模型scale，也不把正式200次场景用于选模。

## 引擎构建和8GB加载

先建立相同模块划分、dtype及控制契约的TensorRT浮点参考，再构建AWQ和GPTQ候选。记录ONNX/parser/TensorRT/CUDA/驱动/ModelOpt版本、容器摘要、插件及profile；不得只记录“latest”。N0依据目标4070和现有服务器兼容矩阵选择具体版本，不直接升级训练环境或GPU驱动。[NVIDIA支持矩阵](https://docs.nvidia.com/deeplearning/tensorrt/latest/getting-started/support-matrix.html)

2026-10-07只读检查：当前服务器为RTX4090、49,140MiB显存、驱动535.129.03；宿主Python未检出TensorRT。这不是所有容器依赖检查，也不是目标4070验收。本轮没有安装或启动模型。

默认优先按目标4070及目标操作系统构建和调优。若在4090构建，必须登记对应版本支持的硬件兼容策略或限制，并在4070真实反序列化、运行和测峰值。同属RTX40系列不保证tactic最优或显存足够；默认engine还绑定构建版本和平台，不能把4090 plan文件视作已可直接部署。[TensorRT引擎兼容说明](https://docs.nvidia.com/deeplearning/tensorrt/latest/inference-library/engine-compatibility.html)

量化制作、图验证和离线build不纳入推理进程8GB验收，但目标设备build若也受8GB限制，应逐子图制作、限制构建工作区并记录失败；不能为了build成功修改推理模型契约。生产只加载已构建engine，不先在GPU加载完整PyTorch／JAX浮点模型，也不常驻第二份GPU权重。

三个engine合计只对应一套模型。视觉多槽共享一个engine；请求串行、单CUDA stream和有界输入队列。对串行执行的context工作区评估共享缓冲，并按同步完成事件保护复用；持久缓冲、KV和插件分配另计。不能只以 `set_memory_pool_limit` 数值推断总显存满足预算。

保存detailed层报告和构建日志，核对实际量化节点、参数覆盖、INT4权重存储、融合与浮点回退。记录engine文件大小、runtime分配及设备总显存。强类型图中数值稳定精度由图的dtype/cast控制，不能把“动作专家不量化”误解为允许任意降低其计算精度。[TensorRT精度控制](https://docs.nvidia.com/deeplearning/tensorrt/latest/inference-library/precision-control.html)

首轮关闭CUDA Graph，先形成冷启动及稳态基线；仅在收益和附加显存均实测合格后启用。服务在ready前完成所有合法shape和10个时间输入的预热。两份模型不能同时驻留，重新加载也需满足进程6.4GB、设备7.2GB预算。

## 实施顺序和放行条件

以下均为未来实施任务，本轮不执行。

| 阶段 | 交付 | 放行条件 |
|---|---|---|
| T0 固定环境和导出契约 | 目标4070信息、版本矩阵、层映射、缓存／shape／时间表契约 | 同源资产与控制参数不漂移；所有精度变化登记 |
| T1 浮点导出 | 三个浮点ONNX及TensorRT子图、完整10步参考 | 图像、前缀K/V、逐步速度场和最终动作分级核对 |
| T2 校准导出 | RTN工程样例、AWQ主候选、GPTQ同范围对照 | 真实数据、合法对称INT4和block布局；失败保留 |
| T3 build和重载 | engine、层报告、profile、timing cache及独立加载入口 | 实际INT4覆盖明确；同一冻结engine重载动作最大差≤1e-6 |
| T4 开发回归和选模 | 动作误差、Panda10任务×3初态、模块与全链延迟 | ≥27/30；相对同后端浮点净损失≤1集，冻结候选 |
| T5 目标设备资源 | 冷启动、预热、1,000次请求、2小时连续运行 | 4070真实测试；进程峰值≤6.4GB，总峰值≤7.2GB，无OOM和持续增长 |
| T6 正式仿真 | 独立Panda10任务×20次；微调后ECO65＋ZhiXing同范围 | 每组≥180/200，较同源浮点净下降≤5个百分点 |
| T7 实机迁移 | 双相机影子推理，再代表任务及扩展闭环 | 动作契约、现场期限、任务质量及异常处理分别通过 |

保留原质量门槛：按冻结合法范围缩放到[-1,1]，运动通道MAE≤0.01、绝对差P99≤0.05；远离夹爪阈值的判定分歧≤0.5%；裁剪率增加≤1个百分点。物理单位容差在正式比较前登记；阈值附近误差另列。分别报告导出误差、量化误差及迭代累积误差，分阶段累计结果也必须满足最终门槛，不能每阶段单独通过就忽略总误差。

独立重载门槛适用于同一冻结engine；重新build可能选择不同tactic，不承诺文件SHA或逐bit输出相同。重build需记录tactic/cache及重新验收，不能借用旧engine的重载成绩。

正式测试报告每任务、配对丢失／恢复和置信区间；单任务低于80%须调查。完整端到端延迟包含相机、预处理、通信、model、反归一化和调度；20Hz每5步重规划的名义间隔250ms，暂以P99≤200ms作为初步目标，按实机观测年龄收紧。4090限显存只是筛查；4070上的显存、延迟和任务成功率必须实测。

原JAX／同源PyTorch／TensorRT浮点／TensorRT量化分别记录。无法统一后端的结果称为整体部署差异；量化影响优先比较同TensorRT浮点参考。浮点参考在8GB设备无法运行时如实登记资源失败，离线误差可用开发服务器参考，但不得给出缺失的同设备加速倍数。

实机先影子推理，再沿用现场已经验证的控制边界做代表任务3类×20次，扩展10类×20次；实际任务集合待实施前确定。量化比较不同时更改异步重规划、控制器或采集行为。所有W4候选质量失败时如实记录失败，另建后续方案；不把旧W8回退结果称为本TensorRT方案通过。
