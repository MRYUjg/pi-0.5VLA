## 1. 前置：N2 的 TCP 修复落地（D2）

N2 判据 (c) 已确认「PandaGripper 下的对齐结论对 ZhiXing 不成立」（平移差 23.000 mm），
且发现 **ZhiXing 的 `grip_site` 落在手指连杆根部**，物理夹持点在沿接近轴 **+82.54 mm**（闭合位）——
即策略的每一条位置指令都让夹持点系统性偏移 65~83 mm。

本轮**同批次**落地两项（必须同时，否则起点会再低 82 mm）：

| 项 | 改动 | sha256 前 → 后 |
|---|---|---|
| TCP 前移 | `robosuite/models/assets/grippers/zhixing_gripper.xml` 的 `<body name="eef" pos="0 0 0.12">` → `pos="0 0 0.20254"` | `e7aab50c66da1e34` → **`c0692e58374b1513`** |
| 配套 `init_qpos` | `eco65_robot.py` 与 `mounted_eco65.py` 两处 → `[-0.12639, -0.222035, -0.841572, -0.563545, 1.563635, -1.697476]` | `4ac890d5359cdb3b` → `27ac09fa640e4fef`；`a9048a371eb2dd8c` → `3c828ad6d6cb4fec` |

* 依据：`0.20254 = 0.120 + 0.08254`，其中 **0.08254 m 取 N2 权威口径**（两指垫**内侧面中点** + 四连杆约束收敛后测量）。
  N2 初版用「最近点对」量得 +66.03 mm 并建议 `0.18603` —— 该口径在平行平面间**退化**、低估 16.5 mm，**已作废**。
* 脚本 `scripts/apply_zhixing_tcp_fix.py`：字节级外科补丁、幂等、`--dry-run`、落盘前校验
  （断言 `eef=0 0 0.20254`、`grip_site=0 0 0`、**N3 的力上限与指垫参数完整保留**）。
* 备份：三个文件各带 `*.pre_tcpfix.bak`。回滚即 `cp <f>.pre_tcpfix.bak <f>`。

**验证**（`scripts/verify_tcp_fix.py`，只读探测）：编译模型 `eef body pos = [0.0, 0.0, 0.20254]` ✅；
Panda+PandaGripper 参考实测夹持点偏移 **−3.60 mm**，与 N2 记载**逐位一致**，交叉验证了测量口径。

**连带影响已核对**：`GRIPPER_STATE_SELECTOR`（`grip_site` 是 site，不参与 state 构造）、
`_important_geoms`、动作维度（仍 7）、关节限位、PandaGripper 资产、以及 ECO65+PandaGripper 的
9/10 基线**均不受影响**。

## 2. 套件决策的实况：`libero_object` 需要一个新的机器人类

D1 决定改用 `libero_object`。落地时发现 suite 的 **arena 类型决定机器人挂载方式**：

| suite | problem 类 | 机器人前缀 | 结果 |
|---|---|---|---|
| `libero_spatial` | Tabletop | `Mounted` | 构建 ✓，但抓取目标可抓 **0/10**（10 个任务全是 107 mm 黑碗 > 90 mm 行程） |
| `libero_goal` | Tabletop | `Mounted` | 构建 ✓，但仅 2/10 真为抓取任务（其余是抽屉/灶台/推盘），且抓取目标是 107 mm 碗 |
| **`libero_object`** | **Floor** | **`OnTheGround`** | 原本 `KeyError: 'OnTheGroundECO65'` ✗ → **新增类后可构建，10/10 任务均有可抓目标** |
| `libero_10` | Kitchen Tabletop | `OnTheGround` | `mj_makeConstraint` 引擎错误，暂不可用 |

**新增 `OnTheGroundECO65`**（`third_party/libero/libero/libero/envs/robots/on_the_ground_eco65.py`，
2970 B，sha16 `328096fd9425c30c`），并在 `robots/__init__.py` 注册。
与 `MountedECO65` 的**唯一差别**是 `default_mount = None` 与 `base_xpos_offset` 增补
`coffee_table`/`living_room_table`（对齐 `OnTheGroundPanda` 的约定）；夹爪、控制器、阻尼、TCP 约定完全一致，
故 N1/N2/N3 的夹爪结论与 TCP 修复对本类同样成立。
落地脚本 `scripts/apply_ontheground_eco65.py`（幂等、dry-run、备份 `*.pre_otg.bak`）。

### 2.1 地面工作区的初始位姿：**无需重解**

`scripts/n4_solve_floor_init_pose.py` 实测：沿用 `MountedECO65` 的 N2 对齐解，
在地面 arena 下 ECO65 夹持点与 `OnTheGroundPanda` 夹持点偏差仅 **0.0938 mm**，
最小关节余量 **1.5424 rad**（与 N2 报值一致）。

原因：`MountedPanda` 与 `OnTheGroundPanda` 的 `init_qpos` 相同，且**两个 arena 里机器人的 base
都在 `(-0.6, 0, 0)`**，故「夹持点相对 base 的位置」与 arena 无关 —— N2 的对齐成果可直接迁移。
（这也说明当初把 TCP 修好是划算的：`grip_site` 与夹持点重合后，位姿对齐才具有跨 arena 的可移植性。）

### 2.2 ⚠️ 新发现：ECO65 在地面 arena 存在**真实的可达性缺口**

按各物体默认摆放实测 IK 可达性（夹持点目标 = 物体抓取位）：

| 物体 | 夹持点目标 (x,y,z) | IK 残差 | 判定 |
|---|---|---:|---|
| `alphabet_soup`（62.4 mm，76.2 高） | (−0.120, −0.244, 0.041) | **0.02 mm** | ✅ 可达 |
| `cream_cheese` / `butter` | (−0.154, 0.063) / (−0.204, −0.080) | 0.02 mm | ✅ 可达 |
| `basket`（投放目标） | (−0.005, 0.262, 0.167) | **80.57 mm** | ❌ 不可达 |
| `salad_dressing` | (0.050, −0.101, 0.135) | 70.25 mm | ❌ |
| `tomato_sauce` | (0.150, 0.027, 0.064) | 117.44 mm | ❌ |
| `milk` | (0.096, −0.195, 0.149) | 133.69 mm | ❌ |

**系统性规律**：可达的是靠近机器人一侧（x 更负）的物体；x 为正的物体距 base 已 >0.7 m。
地面 arena 是**按 7 自由度、更长臂展的 Panda 设计**的，ECO65（6 自由度、更短）覆盖不了整个工作区。
这不是 bug，是**本体限制**，N7 的 200 次评测必须把「不可达」作为独立失败类报告。
本轮试采选的 `alphabet_soup` 位于可达区，故不受影响。

## 3. 采集链路实现（`scripts/n4_collect.py`）

### 3.1 脚本专家

状态驱动的九相位专家，目标点用**真实物体位姿**表达（特权信息，**仅作教师**，评测不得读取）：

```text
settle → approach(抓取点上方 8 cm) → descend(抓取高度) → close(闭合到停住)
      → lift(5 cm，力驱动 OSC) → transport(篮口上方) → place → release → retreat
```

三条来自 N3 的硬约束被严格遵守：

1. **绝不用策略成功率判断**：全程脚本专家 + 底层 OSC，**未加载 π0.5**（策略在 ZhiXing 上有腕部视觉 OOD）。
2. **抬升必须力驱动**：用 OSC 闭环位移，**不用**「直接改写 qpos」的运动学瞬移（后者传不了载荷，是台架假象）。
3. **闭合必须「闭合到停住」**：加力上限后全行程不再瞬时完成，固定步数会在夹爪还张着时就开始抬升。

### 3.2 o_t / a_t 配对（本采集器唯一的正确性核心）

逐帧严格写成「**先取观测、再执行动作**」：

```python
obs_t   <- 上一帧 env.step 的返回（或 reset 的返回）   # 动作**前**
frame_t <- 记录 obs_t（双视角 RGB、qpos/qvel、grip_site）
a_t     <- 本帧要执行的 7 维动作
env.step(a_t) -> obs_{t+1}
frame_t.action <- a_t
```

不使用任何私有接口事后补拍，也不存在「动作后图像配动作前标签」。

### 3.3 采集契约落实

| 契约项 | 落实 |
|---|---|
| 20 Hz | `control_timestep = 0.05`，`timestamp` 严格等间隔 |
| 双视角 RGB | `agentview` 与 `robot0_eye_in_hand`，各 **180° 翻转**（与 `examples/libero/main.py` 一致），记录分辨率与翻转约定 |
| 两路是不同相机 | 实测两路平均绝对差 **81.1~81.8/255** |
| 完整状态 | 全量 `qpos`/`qvel` + 臂/夹爪索引映射 + `grip_site` 位姿 |
| 8 维 state | `[grip_site xyz, 轴角, Left_1_Joint, Right_1_Joint]`，按名字取关节（不按未知索引截取） |
| 7 维动作 | **真正传给 `env.step` 的**世界系 OSC 增量 + 夹爪（−1 开 / +1 合） |
| 原子保存 | 写 `.tmp.npz` 再 `rename`；**已存在则拒绝覆盖** |
| 成功/失败分离 | `raw/success/`、`raw/failure/`，失败不进训练集 |
| 元数据 | 初始完整仿真状态（含求解器 `qacc_warmstart`）、对象初态指纹、任务文字、种子、教师类型、动作尺度、**TCP 定义（eef 位置 + XML 哈希）**、夹爪速度、代码指纹 |
| 成功判定 | 以 **LIBERO 原生谓词**为主，另**独立记录**物体是否真实抬升、是否几何入篮 |

### 3.4 与方案的唯一有意偏离：原始格式用 `.npz` 而非 HDF5

`任务方案.md` P1 **建议**原始记录用 HDF5。但实测 `libero:latest` 运行容器
**没有 h5py，也没有 pip / uv**（`tables`/`zarr`/`pyarrow` 均无），而 venv 位于镜像内、
`--rm` 每次重建，装不进去；若为此重建镜像，会动摇已验证的 9/10 基线与 N0~N3 全部结论。
故改用 **numpy `.npz`（压缩）**：零依赖、数组语义与 HDF5 等价、同样满足
「per-episode 原子保存 + 不覆盖」；N5 转 LeRobot 时再统一成发布格式。

## 4. 根因诊断链：从「抓不住」到 5/5

本轮试采最初 **0/5**，逐项定位后修掉 **6 个真实缺陷**。这一节是本节点最有复用价值的部分。

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 闭合第 1 步 `Left_1` 从 −0.0008 跳到 −0.54，物体被**拨飞 0.44 m** | `ZhixingGripper.speed = 0.2` → 夹爪在 ~2 个 env step 内闭死（≈900 mm/s，**远超厂商规格 <100 mm/s**） | 采集时设 `speed = 0.01`（与 `PandaGripper` 同值），闭合渐进可控；**该值写入每条 episode 元数据** |
| 2 | 抓取高度不确定 | 未标定 | 扫描：`grip_site` z ∈ **[20, 44] mm 均可抓**，52 mm 打飞（指垫落到罐顶沿之上） |
| 3 | 抬升成功但投放失败 | 篮子中心 x≈0 距 base 0.65 m，**已超可达边缘** | 投放点改到**朝机器人一侧的近边** |
| 4 | 投放时物体被蹭掉 | 下潜进篮时物体必须穿过篮口，横向误差即刮篮沿（实测抓取 10/10、投放仅 3/10） | 改为**篮口上方释放**，物体自由落入 |
| 5 | 搬运途中滑落 | 高速横移惯性超过保持力余量（N3 测得 μ_eff 仅约名义值一半） | 搬运/投放段伺服增益 **gain = 0.55**（动作仍为合法 7 维 OSC 增量）。修后 **5/6 = 83%** |
| 6 | 5 条示范其实是**同一初始化** | `env.seed(s); env.reset()` 对 `libero_object` 的**目标物体**几乎不改变摆放（seed=8/9/10 物体中心都是 (−0.119, −0.2435)，只有篮子在变） | 显式在 BDDL `initial_state` 区域内**拒绝采样**重摆物体（保证两两 ≥12 mm） |

### 4.1 三个踩过的坑（记录以免重蹈）

* **`initial_state` 用对象名、body 名带 `_main` 后缀**：按 body 名匹配区域永远匹配不上（静默返回 `None`，
  5 条示范会退化成同一初始化）。
* **采样时直接写纯偏航四元数会把物体弄倒**：实测罐头由「高 76.2 mm 立着」变成「高 62.5 mm 躺着」——
  说明模型初始四元数并非单位四元数。正确做法是**左乘一个世界 z 偏航**，保留原有姿态。
* **初始化重摆必须放在「开始记录」之前**：它是对 free joint 的直接写入，**无法用 7 维动作解释**。
  放在记录开始之后，episode 里就存在一处无法解释的状态跳变，回放必然发散（实测 qpos 偏差 0.63~1.36）。

**关于回放验证的诚实说明**：审计会从 episode 的完整初始状态重放 `actions` 并逐步比对 `qpos`。
结果：**自由空间段可复现到 ~5×10⁻³ rad**（3 条），另 2 条因接触在窗口内提前发生而发散到 O(1)。
刚体接触是**混沌系统**，初始状态里任何未被格式捕获的自由度（求解器内部工作区、控制器私有缓存）
都会被放大；因此该指标**记录为证据、不作为硬判据**，`o_t/a_t` 的正确性由不依赖重仿真的
**错位对照检验**独立保证（lag0 一致率 ≈1.0；错位一帧会显著下降）。

## 7. 边界与遗留问题

| # | 项 | 说明 |
|---|---|---|
| 1 | **只覆盖 7/10 个任务** | `libero_object` 的 10 个抓取目标中，`cream_cheese`(17.9 mm 高)、`butter`(17.4)、`chocolate_pudding`(27.4) 三个太扁，不满足「高 ≥45 mm 保证指尖净空」的**顶抓**条件。是否可用**侧向抓取**（手指横向伸出、不受地面净空限制）尚待验证。 |
| 2 | **夹爪速度是配置更改** | 采集用 `speed=0.01`（资产原值 0.2）。理由：0.2 对应 ≈900 mm/s，远超厂商规格 <100 mm/s，且会把物体拨飞；0.01 与 `PandaGripper` 同值。**该值已逐条写入元数据**，但「部署配置到底用哪个」需确认，且训练/推理必须一致。 |
| 3 | **可达性缺口** | §2.2 的 ECO65 地面可达限制是本体固有限制。N7 需把「不可达」列为独立失败类；若影响过大，需考虑任务集或工作区调整。 |
| 4 | **存储量** | 每条 ~90 MB（npz 对图像的压缩比仅 ~2.2×）。方案目标 500~1000 条 → **45~90 GB**（数据盘可用 307 GB，短期可行但需规划）。N5 前建议改用 PNG 编码或转 LeRobot 时统一压缩。 |
| 5 | 采集规模 | 本轮只做**单任务试采**（方案要求「先在一个任务完成至少 5 条」）。扩展到 10 任务 × 50~100 条属 N5。 |
| 6 | 策略侧视觉 OOD | 本节点**未涉及**；仍需 N6 用自数据微调解决。 |
| 7 | 真机 | 零验证。 |
| 8 | `libero_10` | 当前 `mj_makeConstraint` 引擎错误，未追查（本轮不需要）。 |

## 9. 一句话

**N4 的答案是：采集链路已完全打通 —— 先把 N2 的 TCP 定义错误（夹持点偏 109 mm）连同配套初始位姿一起落地，
再为 `libero_object` 补上缺失的地面挂载机器人类 `OnTheGroundECO65`；
然后逐项修掉 6 个真实缺陷（夹爪速度非物理地快、抓取高度未标定、投放点超可达、下潜刮篮口、
横移滑落、初始化根本没变），最终在 task 0 上采到 5/5 条不同初始化的真实成功示范，
契约审计 5/5 通过、o_t/a_t 配对一致率 ≈1.0。**
仍未覆盖的是：另外 3 个扁平物体的抓取策略、ECO65 在地面 arena 的可达性缺口、以及策略侧的视觉 OOD（留待 N6）。
