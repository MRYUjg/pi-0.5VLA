## 5. 两项新发现的证据与含义（本轮重点）

### 5.1 搬运段伺服从不收敛 → N3 与 N4 的成功口径互相矛盾

从 `n3_osc_full_chain.json` 全部 36 次试验的 `phase_end` 独立重算：

| 量 | 值 |
|---|---|
| `transport` 收敛标志为 True 的次数 | **0 / 36** |
| `transport_residual_m` | min **0.0186**、median **0.0531**、max **0.0639**（判据 tol = 0.008 m） |
| `place_residual_m` | min 0.0047、median 0.0055、max 0.0066 |
| `reach_limited=True` | **35 / 36** |

`scripts/n3_osc_full_chain.py` 第 906–931 行的 `gates` 里**没有** `transport_converged` / `place_converged`（只有 `approach_converged`、`descend_converged`、`reorient_converged`），`success = all(gates.values())`；而 `scripts/n4_collect.py` 第 871–884 行把 `approach/descend/lift/transport/place` 任一超时都记为 `servo_no_timeout=False`，再进 `success = predicate and in_basket and stable and servo_no_timeout`。

后果：

1. N3 记的「试块 10/10」在**当前生产口径（N4）下会全部被判失败**；两个节点的通过判据不一致。
2. 前一份记录把「试块 10/10×3＋5/6」与「真实物 0/5」并列，但**没有指出试块那一侧的 10/10 建立在一个已被 N4 否定的口径上**。
3. `reach_limited` 是 N3 自己写出的「到达受限」标志，36 次里 35 次为真，同样未进入任何闸门。

### 5.2 N4「n4v8 0/6」的真实原因

容器内直接读 `raw/failure/n4v8_*.npz` 的 `_meta_json`（不依赖任何摘要 md）：

| seed | frames | lifted_mm | close_steps | success_predicate | geometric_in_basket | servo_timeouts | success |
|---|---|---|---|---|---|---|---|
| 1 | 600 | 48.71 | 10 | false | true | transport 220 + place 160 | false |
| 2 | 521 | 48.50 | 10 | true | true | transport 220 + place 160 | false |
| 3 | 517 | 49.01 | 10 | true | true | transport 220 + place 160 | false |
| 4 | 523 | 50.44 | 10 | true | true | transport 220 + place 160 | false |
| 5 | 521 | 49.63 | 10 | true | true | transport 220 + place 160 | false |
| 6 | 529 | 49.90 | 11 | true | true | transport 220 + place 160 | false |

**6/6 的拒收原因都是伺服超时，不是抓取失败。** 把它概括成「n4v8 采集 0/6 失败」会让人误读为夹爪/抓取问题；应写成「**采集链路在搬运/投放段的伺服收敛不达标，6/6 被自身判据拒收**」。

同时 `transport` 每次都耗满预算（220 步）、`place` 每次耗满 160 步，与前记录 §4 提到的「复核曾实测 transport 恒耗满 220 步、place 恒耗满 160 步」一致 —— 说明这是**系统性控制问题**而非偶发。

## 6. 阻塞项：退出码 139/134 的定位结果

### 6.1 已复现

在容器内以**生产入口** `scripts/gl_backend_probe.py`（同一 `build → reset → 60 步`路径）复跑：**OSMesa 与 EGL 都在写完结果 JSON 之后崩于 `free(): invalid pointer`，退出码 134（SIGABRT）**。此前记录的 OSMesa 139 属同一故障。

### 6.2 已把范围缩到「解释器清理阶段」

容器内变体矩阵（每格一次独立 `docker run`，只写容器 `/tmp`）：

| 变体 | 做法 | 退出码 |
|---|---|---|
| B | 20 步后**不调用** `env.close()`，直接 `os._exit(0)` | **0** |
| C | `env.close()` → `del env` → `gc.collect()` → `os._exit(0)` | **0** |
| D | `env.close()` → 把 `MjModel.__del__`/`MjData.__del__` 置空 → `os._exit(0)` | **0** |
| E | `env.close()` → `os._exit(0)` | **0** |
| H | 事先把 `MjModel.__del__`/`MjData.__del__` 置空，然后**让解释器正常退出** | **139** |
| 基线 | 不干预，正常退出 | 139/134 |

判读：**崩溃发生在「进程退出、C 扩展对象被析构」这一段**，而不是仿真/渲染过程中；`os._exit(0)`（跳过 Python 终结与 C 析构）能稳定拿到退出码 0，且已落盘的结果文件完整（n4v8 六条 episode＋summary 都在）。变体 H 把 `__del__` 置空仍崩，说明触发点不在 Python 层的 `MjModel.__del__`，而在更底层的 GL/OSMesa 上下文清理 —— **根因仍未定位到具体库，但已从「未知」缩到「退出析构路径上的堆损坏」**。

### 6.3 必须同时记账的两点

1. 按本项目约定「不得以忽略退出码的方式绕过」，`os._exit(0)` 只能作为**有记录的工程绕过**，不能当作「问题已解决」写进验收；它同时也掩盖了 `env.close()`/上下文释放是否真的干净。
2. **即便绕过退出码，CPU 动态仿真的吞吐也不支持原计划的批量采集**：本轮实测该路径 **5.28–5.44 步/秒**（约 0.18–0.19 s/步），仅为 20 Hz 控制要求的 **0.26–0.27 倍实时**；`/dev/dri/renderD128` 存在但 EGL 与 OSMesa 同速，说明当前拿到的是软件渲染。折算：单条 ~520 帧 episode ≈ 97 s（与 n4v8 实测 293.5 s/6 条 ≈ 49 s/条同量级）；P1 的 500–1000 条示范需 **7–14 小时**纯采集，P4 的 200 次正式评测需 **≈2.9 小时/策略**。这是资源事实，应在 P1 启动前与用户确认。

> 服务器资源：8 核 Xeon E5-2698 v4、内存 **15 GB**（可用约 13 GB），`/mnt/data` 剩余 302 GB。采集器把整条 episode 的图像缓存在内存后再写盘（`n4_collect.py` 的 `Episode.frames`），单条约 100 MB，与 15 GB 内存约束需要一起核算。

## 7. 建议的收口顺序（在既有 P0 建议之上修订）

1. **先定口径，再修控制**：明确「搬运段是否必须收敛」。要么把 N4 的 `servo_no_timeout` 写入 N3 闸门（则现有 10/10 作废），要么在文档里正式说明 N3 不判搬运收敛并给出理由与替代判据。二者只能选一，不能两套并行。
2. **查搬运段 0/36 不收敛的性质**：目标点 `above = [bx, by, rim_z+0.12]`，残差中位数 53 mm 且 `reach_limited=35/36`。先判定是**运动学不可达**（篮子位置超出单臂工作空间）还是**控制器饱和/增益不足**。这决定 P0 是「修控制」还是「改任务布局」。
3. **真实目标物抓取**：按 `akita_black_bowl_1` 的薄壁曲面改抓取策略（避免让 0.57 mm 净开距的指垫去捏 2.5–3.2 mm 壁），或换更合适的 BDDL 目标物，并明确记录「换物」是方案变更而非通过。
4. **补 `parts.A`（空载开闭 ×10）**：脚本已实现，只需按 `n3_grasp_test.py --part A` 跑一次并保留产物；顺带把 `speed=0.2` 下不闭合的现象写进 N1 结论。
5. **退出码**：先把根因钉到具体库（可用容器内 `gdb --batch -ex bt` 抓 abort 栈）；在根因闭合前，若必须跑批，使用**显式记录在案的** `os._exit(0)` 包装，并在产物里同时记录「原始退出码」。
6. **文档收口（受管文件，须显式建 r5）**：索引页 4 处 r3→r4；`current.json` 的 `N0_status` 与 manifest 的 `SOURCE_BASELINE_SEALED` 统一；把 `results/n3_osc_reorient_diagnosis.md` 同类问题一并清查（`gripper_polarity.json` 亦需作废标注）。
